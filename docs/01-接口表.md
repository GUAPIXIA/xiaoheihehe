**证据标记**：【源码】= 上游源码中存在 ｜【网页】= 官方网页版 JS 中观察到调用 ｜【实测】= 本次真实只读请求验证成功 ｜【待验证】= 需登录/验证码或未取得证据 ｜【未找到】= 检索过且不存在。

**通用约定**
- 基址：`https://api.xiaoheihe.cn`（`crates/xhh-core/src/lib.rs` `BASE_URL`）**【源码】**
- 全部接口均为 `GET`（除标注 `POST` 的写入接口）；响应均为 `application/json`，HTTP 通常恒为 **200**，业务状态在 body 的 `status` 字段 **【实测】**。
- 所有请求必须携带第 0 节列出的公共参数与 hkey 签名 **【实测】**。

### 0.1 网页端真实的参数拼装（**静态还原**，证据 `research/web_endpoints.md` §A/§B）

参数名在主 bundle 里被字符串数组混淆（`Ss=["a","b","e","g","h","i","m","n","o","p","q","r","s","t","u","w"]` 拼出 `hkey`/`_time`/`nonce`），因此**直接 grep `hkey` 会 0 命中**。还原后，网页端每个请求带两组参数：

1. **平台参数**：`app=heybox`、`heybox_id`（读 cookie）、`os_type=web`、`x_app=heybox_website`、`x_client_type=web`、`client_type=web`、`x_os_type=<Mac|Windows|Android|iOS|ohos>`、`web_version=<meta name="web_version" content="3.0">`、`device_id=<fingerprintjs visitorId>`
2. **签名参数**：`version="999.0.4"`（常量）、`hkey`、`_time`、`nonce`

**与上游 `xhh-core` 的公共参数差异（实测均不影响只读接口）**：

| 差异点 | 网页端实际 | `xhh-core` | 实测结论 |
|---|---|---|---|
| `device_info` | **全局不带**（仅 `/bbs/app/link/related/recommend_web` 显式传 `"Chrome"`） | 恒带 `device_info=Chrome` | 多传无害 ✅ |
| `_notip` | **全 bundle 0 命中** | 恒带 `_notip=true` | 多传无害 ✅ |
| `web_version` | 读 HTML meta，实测为 `3.0` | 硬编码 `2.5` | 只读接口两者都通过 ✅ |
| `x_client_type` | `kq()` 里是 `weboutapp`，但被启动插件覆盖为 `web` | `web` | 与网页最终值一致 ✅ |
| `x_client_version` | Web 分支**不带** | 不带 | 一致 ✅ |

**签名时间戳的一个歧义（重要）**：网页端签名函数是 `zM.g = (e,t,n) => Tr(e, t+1, n)`，即**用 `_time + 1` 作为签名时间戳**；而上游 `xhh-core` 用 `offset` 参数（feeds=0、发帖=1）。**本次实测用 offset=0 对 `/bbs/app/feeds` 等只读接口全部成功** → 说明服务端容忍 ±1 秒的时间戳偏差。接入建议：按 `xhh-core` 的 offset 约定（发帖类=1，其余=0），并对失败请求做一次 `_time+1` 重试。

**`nonce` 的推导方式不同但服务端不校验**：网页端 `nonce = MD5(秒级时间戳 + 毫秒时间戳 + Math.random() + 指纹 + 指纹).toUpperCase()`；`xhh-core` 用 `MD5(timestamp + randint(0,1e9)).toUpperCase()`。**本次实测直接用后者的公式即可通过** → 服务端只校验 `nonce` 的**格式（32 位大写十六进制）**，不校验其推导过程。

**请求头与认证**：网页端**没有任何自定义 `X-*` 头、没有 `Authorization`、没有 token 头**；axios 实例以 `withCredentials:true` 依赖 **Cookie** 认证（`research/web_endpoints.md` §D）。`x_xhh_tokenid` 由客户端**写入** cookie（14 天有效），源码中**未见读取它的代码**（`xhh-core` 则本地生成它）。

**第二套签名 `_rnd`（仅评论创建使用）**：当请求 config 显式带 `{rnd:"15"}` 时追加参数 `_rnd = "15:" + HMAC_SHA256_hex(key="Z7mFG4tQp9Ws2LxB8H", msg=key + nonce + (_time + ":" + nonce))`（64 位小写十六进制）。源码中**只在 `/bbs/app/comment/create` 观察到 1 处调用点**。`xhh-core` **未实现**该签名 → 发评论可能因此失败（见 `03-xhh-core覆盖与复用.md`）。

**必须额外处理的响应状态**（网页端响应拦截器，`research/web_endpoints.md` §D）：

| `status` | 含义 | 网页端处理 | 本次实测 |
|---|---|---|---|
| `ok` / `failed` / `login` / `show_captcha` | 见文末失败形态表 | `show_captcha` → 加载腾讯 TCaptcha（appid `199251710` 命中 bbs 白名单 / `2061805035` 默认）；`login` → 引导登录 | ✅ 均观察到 |
| **`lack_token`** | token 缺失/过期 | 调用 `setXHHTokenIDWithSDK()` 重新获取 tokenid 后 `need_recall` **重放一次原请求** | 🔴 **【待验证】**（本次未触发） |

**接口域名选择表**（主 bundle `Pk`，`research/web_endpoints.md` §10）：`heybox_app → https://api.xiaoheihe.cn`（默认，纯浏览器 fallback）、`heybox_acc → https://accapi.xiaoheihe.cn`、`heybox_chat → https://chat.xiaoheihe.cn`、`heybox_workshop → https://workshopapi.xiaoheihe.cn`、`maxjia_app → https://v5api.maxjia.com`、`heybox_egg → https://web.xiaoheihe.cn`。

## 9. 上游自带 HTTP 服务的本地路由（**不是**小黑盒接口）

`xhh-http` 暴露的 35 个端点（`crates/xhh-http/src/routes/mod.rs`）是它**自己**的 REST 服务（`/api/auth/*`、`/api/feeds`、`/api/post/*`、`/api/comment/*`、`/api/like/*`、`/api/favour/*`、`/api/user/*`、`/api/search/*`、`/api/emoji`、`/api/notifications`、`/api/agent/*`），**不需要也不可能被我们的 Tauri 客户端复用**（除非我们选择以 sidecar 方式跑它，但那会带来 GPL 传染性，见 03 节）。README 中"35 个 REST API 端点 + Swagger UI"指的是这部分，**与小黑盒上游接口无关**。
