对应需求：「核心需求是按社区／分区过滤：支持多选"只看这些社区"和多选"屏蔽这些社区"，设置在本地保存。」

## 2. 三个候选数据源的实测特性对比（决定架构的关键）

| 特性 | `/bbs/app/feeds`（综合流） | `/bbs/app/topic/feeds`（社区·社区 tab） | `/bbs/app/topic/feeds/news`（社区·头条 tab） |
|---|---|---|---|
| 能否按社区限定 | ❌ 只有**软加权** | ✅ 单社区 | ✅ 单社区 |
| **归属严格性（实测）** | ❌ 3/11 命中 | ✅ **109/109**（5 个样本） | ⚠️ **36/37**（1 条属别社区） |
| **确定性（两次相同请求）** | ❌ **交集 0/10** | ❌ **交集 0/18** | ✅ **19/19 且顺序一致**（第二页重复请求亦 100% 一致） |
| 可用游标 | `offset`（网页端 +30） | `offset`（`lastval` **恒为空**） | ✅ **`lastval`（13 位毫秒时间戳）** |
| `limit` 是否生效 | ❌（约 10–11 条/页） | ❌（约 17–20 条/页，但**必传**） | ❌（固定约 19 条/页） |
| 条目时间字段 | `create_at` + `modify_at` | `create_at` + `modify_at` | ⚠️ **无 `create_at`**，只有 `modify_at` + `formated_time`（相对时间文本） |
| 嵌套作者对象 | ✅ `user{userid,username,avatar,...}` | ✅ | ❌ **无 `user`**，只有 `userid` |
| 广告/推荐卡片 | ⚠️ 有（`content_type=18`，无 `linkid`） | 无（实测全为 `content_type=4`） | 无（实测全为 `content_type=1`） |
| 证据 | `report4.md` §1/§3、`analysis3.md` | `report4.md` §2/§5、`analysis3.md` | `report6.md` §4、`report7.md` §1–2 |

**结论：只有 `/bbs/app/topic/feeds/news` 能同时满足「归属基本严格 + 确定性 + 可靠游标」**，它是"只看这些社区"的**主数据源**。另外两个源只能作为补充或"发现"模式，**不能承诺稳定的分页与去重**。

## 3. 推荐架构：以「社区头条」为地基的本地聚合

```
本地设置 (本地持久化)
  includeTopicIds: number[]   // 只看这些社区（空 = 不限制）
  excludeTopicIds: number[]   // 屏蔽这些社区（优先级高于 include）
  unknownCommunityPolicy: 'keep' | 'hide'   // topics[] 为空时怎么办
  sourceMode: 'community' | 'feed' | 'both'
```

### 3.1 数据获取（`sourceMode = 'community'`，默认推荐）

对 `S = includeTopicIds \ excludeTopicIds` 中的**每个社区**独立维护游标：

```
cursor[c] = ""            // 首次为空
GET /bbs/app/topic/feeds/news?topic_id=<c>&limit=20&lastval=<cursor[c]>
→ items[c] = result.links
→ cursor[c] = result.lastval     // 下一页游标
```

- **并发**：`S` 可能有几十个社区。首屏只并行拉取**当前可见的 N 个社区**（建议 ≤8），其余按需懒加载；对每个社区的结果做 **TTL 缓存（建议 5–10 分钟）**，避免每次滚动都打 N 次请求。
- **终止条件**（每个社区独立判断，任一满足即停）：
  1. `result.links` 为空；
  2. `result.lastval` 为空或与上一次**相同**（游标不再前进）；
  3. 本页条数 < 上一页条数（服务端已到尾部）。
- 该接口是**确定性**的，所以同一 `lastval` 重复请求可安全重试，不会引入重复或空洞。

### 3.2 归并、去重、排序

```
all = ∪ items[c] for c in S
1) 去重：按 linkid（Set<number>）
   ⚠️ 跨社区重复是**预期行为**：一篇 topics=[425422, 43] 的帖子会同时出现在两个社区的列表里
2) 社区过滤（本地）：
   - 若 topics[].topic_id ∩ excludeTopicIds ≠ ∅  → 丢弃（**屏蔽优先**）
   - 若 includeTopicIds 非空 且 topics[].topic_id ∩ includeTopicIds = ∅ → 丢弃
   - 若 topics[] 为空 → 按 unknownCommunityPolicy 处理（见 §5）
3) 丢弃非帖子卡片：content_type === 18 或 缺少 linkid
4) 排序：使用 modify_at 降序（**唯一可用的数值时间字段**）
   ⚠️ 头条列表**没有 create_at**，只有 modify_at 与 formated_time；
      formated_time 是服务端渲染的相对时间文本（"16分钟前"），缓存后会失真，不要用它排序
   ⚠️ 同一社区内部保持服务端返回顺序作为权威；跨社区的顺序只能"尽力而为"
```

### 3.3 内容不足时的**有限补页**（关键约束）

因为要去掉屏蔽社区与（可能的）未知社区，"拉一页 → 过滤后不够一屏"是常态。补页策略：

```
target = 一屏所需条数（例如 20）
round = 0
while (结果条数 < target) and (round < MAX_ROUNDS) and (仍有社区可继续):
    并行续拉所有"未终止"社区的下一页（cursor[c]）
    归并去重过滤
    round += 1

建议 MAX_ROUNDS = 2~3，且单次刷新每个社区最多 3 次请求
```

- **为什么必须有上限**：`S` 大 + `excludeTopicIds` 大时，理论上可以无限补页（每个社区本身是近 20 条/页）。无上限会造成请求放大与风控风险。
- **补页不足时的 UI 处理**：显式提示"已按筛选条件加载完（N 条）"，而不是静默显示空白或无限转圈。
- **保留原始游标**：补页过程中**不要**因为过滤结果为空就重置 `cursor[c]`；游标只按服务端返回推进，这样"放宽筛选条件"时能立刻复用已拉取的数据（配合按 `linkid` 的本地缓存）。

### 3.4 `sourceMode = 'feed'`（综合流，作为"发现"模式）

`/bbs/app/feeds` **只有本地过滤一条路**，且必须接受它的三个硬约束：

```
GET /bbs/app/feeds?pull=0&offset=<offset>&dw=<宽度-56>
offset += 30        // 网页端步长
```

- **不能承诺确定性**：同一 `offset` 两次请求返回的集合交集为 0 → 每次刷新都会出现"新帖子"，也会**漏掉**一些帖子。UI 上应把它标为"推荐/发现"，不要承诺"完整时间线"。
- **本地过滤**：与 §3.2 同一套规则（`topics[].topic_id` 命中判断 + `content_type=18` 丢弃）。
- **补页**：同一套有限补页（`MAX_ROUNDS` 建议 3，即最多 4 页 ≈ 40 条原始数据 → 过滤后可能只剩几条）。
- **去重**：按 `linkid`；但由于该流非确定性，去重只能避免**本次会话内**重复，无法保证不重复出现。

### 3.5 多社区"只看"的另一种可选形态：每个社区一个 Tab

网页端本身就是**一个社区一个页面**（路由 `/app/topic/link/:topic_id`），社区内有 `社区(link)` / `头条(news)` 两个 tab（来自 `/bbs/app/topic/menu`）。
把"多选社区"实现为**多社区聚合时间线 + 可切换的单社区视图**，既贴合官方交互习惯，也能在聚合页出现问题时降级到单社区稳定列表。

## 5. 缺失分区信息时的处理建议（**不猜测字段含义**）

实测确认存在三类"社区信息缺失/不唯一"的情况：

| 情况 | 观测 | 建议处理 |
|---|---|---|
| `topics` 为**空数组** | 综合流每页 1–3 条；`analysis3.md` §3 | 提供显式设置 `unknownCommunityPolicy`：**默认 `keep`**（保留并标注"社区未知"），用户可选 `hide`。**不要**用标题/关键词猜社区 |
| 条目是**广告/推荐卡片** | `content_type === 18` 且无 `linkid`；网页端自己也是 `filter(t=>t.content_type!==18)` | **一律丢弃**（不是帖子，无社区归属） |
| 帖子**属于多个社区** | 实测 `(43,748366)`、`(53182,608630)`、`(425422,43)` 等 | ① 去重按 `linkid` ② 屏蔽判定用"**任一命中即屏蔽**"（排除优先）③ UI 可显示全部社区名（`topics[].name`） |

**明确不要做的事**（本次未取得证据，不得猜测）：
- 不要假设 `link_tag` 是社区分区（它是内容形态，见 `00` 节 §3.2）。
- 不要假设 `post_tag`（仅头条列表出现，字符串）的含义 —— 本次**未验证**其语义。
- 不要假设 `list_content_tags` / `content_tags` / `act_hashtags` 能代表社区归属 —— 它们是展示/活动标签。
- 不要假设 `h_src`（Base64 埋点串）里能解析出社区 —— 它是埋点数据，非契约字段。
- 不要假设 `topics[].hot_value_v2` / `app_id` 的语义与用途。

## 6. 设置持久化

- 结构建议（与官方无关，纯本地）：
```json
{
  "communityFilter": {
    "includeTopicIds": [7214, 425422],
    "excludeTopicIds": [73906],
    "unknownCommunityPolicy": "keep",
    "sourceMode": "community"
  },
  "communityCache": [
    { "topicId": 7214, "name": "盒友杂谈", "picUrl": "...", "cachedAt": 1791609484 }
  ]
}
```
- 按你的项目需求「用户信息存储尽量保存在安装位置」：建议放在**安装目录下的 `data/`**（如 `<InstallDir>\data\settings.json`），登录凭据单独放 `credentials.json` 并限制权限。⚠️ 注意 `xhh-core` 默认写 `%APPDATA%\xhh\config.json`，**不符合该需求**，需自行实现存储层。
- 社区目录（`topic_id → name/pic_url`）应缓存，避免每次启动都请求；`topic/categories` 返回的 `latest_hot_topics` 可能随热点变化，缓存需带 TTL 并允许手动刷新。

## 7. 限制清单（必须向使用者说明）

1. **无服务端排除能力**：屏蔽社区 100% 在本地完成，被屏蔽内容仍会被下载（流量与隐私影响）。
2. **无多社区单请求**：`k` 个社区 = `k` 个请求，社区多时首屏延迟与请求量线性增长 → 必须做并发上限 + TTL 缓存 + 懒加载。
3. **综合流非确定性**：`/bbs/app/feeds` 重复请求结果不同，**不能**承诺"完整/不重不漏"的时间线。
4. **社区列表非确定性**：`/bbs/app/topic/feeds`（社区 tab）同样非确定性，`offset` 翻页会重不漏 → 不建议作为主时间线。
5. **头条列表覆盖不全**：`news` 是社区"头条"（服务端筛选/智能排序），**不等于该社区的全部帖子**；`xhh-core` 没有更好的替代源。若要"某社区全部帖子"，目前**没有**已验证的稳定接口 → 列入待验证（见 `06`）。
6. **头条条目字段更少**：无 `create_at`、无嵌套 `user` → 列表页如需显示精确发布时间或作者名，得**额外逐个请求**（`/bbs/app/profile/user/profile?userid=`）或改用带 `user` 的 `topic/feeds`（但那个非确定性）→ 建议列表页只用 `formated_time` + `userid`，详情页再补全。
7. **头条列表归属不是 100%**：实测 36/37，仍会有极少"非本社区"条目混入 → 本地过滤**必须**以 `topics[].topic_id` 再做一次核验，不能信任"这个接口返回的一定属于该社区"。
8. **帖子详情需要登录**：`/bbs/app/link/tree` 匿名返回 `show_captcha` → 未登录时聚合列表可用，但点进详情不可用（详见 `06`）。
